D1

Agentic Architecture & Orchestration

WEIGHT~27% · largest domain
MOCK-6016 questions
DRAW-185 questions
BASISCourse material + your trainer
This is the single biggest domain on the exam, and the one most questions dress up as something else — a tool-design or prompting question — when the actual failure is architectural. If a scenario shows an agent doing the wrong thing, check orchestration first.

1. The agentic loop — mechanics

Cert The core loop: send messages + tools → Claude returns a response → check stop_reason → if "tool_use", execute the requested tool(s), append the results as a user message, and call again → if "end_turn", you're done.

The three loop-termination anti-patterns — know these cold:

  1. Parsing the assistant's natural-language text for completion signals ("I'm done," "Task complete") instead of checking stop_reason.
  2. Using an arbitrary iteration cap as the primary stop condition rather than a safety backstop.
  3. Treating the mere presence of assistant text as evidence of completion — text and tool calls can coexist in the same message.
Exam framing: any option that says "check if the response contains the word 'done'" or "stop after N tool calls" as the main control mechanism is bait. The correct mechanism is always stop_reason.

2. Subagents — the orchestration primitive

Cert Subagents are separate Claude instances the lead agent spawns for focused subtasks. The defining property: a subagent's context window starts completely fresh.

What a subagent inherits — the highest-yield fact in this domain

  • Cert It does not automatically receive the parent's conversation history, system prompt, or the parent's preloaded skills.
  • Cert The only channel from parent to subagent is the prompt string in the spawn call. File paths, prior findings, error messages, decisions — all must be written explicitly into that prompt.
  • Likely It does receive: its own system prompt, environment details Claude Code appends, the CLAUDE.md/memory hierarchy, a git-status snapshot from session start. The two built-ins — Explore and Plan — deliberately skip CLAUDE.md and git status to stay fast and cheap.
  • Cert On return: only the subagent's final message goes back to the parent. Every intermediate tool call, every file it read, stays inside the subagent.

Spawning mechanism

Guess Historically called Task, renamed Agent in Claude Code v2.1.63 — shipping product and older grounding material may disagree on the name. The tool name must be in allowedTools for a coordinator to spawn subagents at all.

Cert Parallel execution: multiple subagent calls emitted in a single coordinator response run concurrently. Emitting them across separate turns forces sequential execution instead. A subagent cannot spawn its own subagents.

Three definition methods: (1) programmatically via an agents parameter, (2) filesystem markdown in .claude/agents/, (3) the built-in general-purpose subagent, no definition required.

3. Workflows vs. Agents — the core decision rule

Workflow = you know the exact steps in advance → hard-code the sequence. Agent = steps aren't knowable in advance → give Claude general tools and let it plan dynamically.

Decision matrix — this table is a direct exam trap target
DimensionWorkflowAgent
StepsPredeterminedDynamically planned
TestabilityEasier — known pathHarder — unpredictable
InputsUser supplies specific inputsAgent derives its own, can ask for more
Completion rateHigher (structured)Lower (delegated complexity)
Default choiceYes — reliability firstOnly when genuine flexibility required
Trap: agents have a stated lower completion rate than workflows. A scenario offering an agent solution to a well-defined, repeatable task is very likely wrong — "agent = more capable = better" is exactly the intuition being tested against.

Named workflow patterns

  • Evaluator–optimizer: producer generates, evaluator scores/critiques, loop until accepted.
  • Parallelization: split a multi-factor decision into independent parallel sub-calls, then aggregate.
  • Chaining: sequential separate calls. Trigger: Claude keeps partially violating a constraint-heavy prompt no matter how many times you repeat the constraint — generate first, accept the imperfect output, then run a targeted rewrite pass against the specific violations found.
  • Routing: a cheap first call classifies input, then dispatches to a category-specific pipeline.

Agent design principles

  • Abstract, general-purpose tools beat hyper-specific ones — bash/web_fetch/file_write (broad, recombinable) vs. a hypothetical refactor_tool (narrow).
  • Environment inspection is mandatory for agents — since an agent can't fully predict its own action's result, it must observe the new state afterward.

4. Judgment layer — how D1 questions get you

  • OVER-ENGINEERING in orchestration: a routing classifier or "supervisor agent" fixing what a better task decomposition or sharper subagent prompt would fix directly. Cue: "most effective first step" → cheapest root-cause fix wins.
  • WRONG PROBLEM — the domain's signature trap: a subagent gets blamed for a bad result when the actual failure was the coordinator's narrow decomposition. The subagent did exactly what it was told; what it was told was incomplete.
  • DISPROPORTIONATE: "terminate the whole run," "re-run every subagent," "escalate every case" when a scoped retry would do.
  • PROMPT-HOPE: guaranteed sequencing/handoff between agents controlled only by a system-prompt instruction to "please pass along X."
Quick-reference / rapid recall
  • Continue on stop_reason == "tool_use"; stop on "end_turn" — never parse text, never rely on an iteration cap as the primary stop.
  • Subagents inherit nothing automatically except their own system prompt + environment details + CLAUDE.md/git snapshot — findings must be passed explicitly in the spawn prompt.
  • Only the subagent's final message returns to the parent.
  • Parallel subagents = multiple spawn calls in one turn, not across turns.
  • Workflows: reliability, predetermined, higher completion rate, default choice. Agents: flexibility, dynamic, lower completion rate, only when steps are genuinely unknowable.
  • Named patterns: evaluator-optimizer, parallelization, chaining, routing.
  • The domain's signature exam trap: blaming the subagent/tool/model when the coordinator's decomposition was the actual root cause.
D2

Tool Design & MCP Integration

WEIGHT~18% · smallest core domain
MOCK-6011 questions
DRAW-183 questions
BASISYour own trainer's D2 cheat sheet
Your own post-mock diagnostic flagged this as your weakest domain (73%). Smaller question count than D1/D3/D4 raises the cost of every miss.

1. Tool descriptions are the selection mechanism

Cert The single most important fact in the domain: vague tool descriptions cause misrouting between similar tools. The fix is always to sharpen the description — purpose, inputs, when to use this tool vs. its alternatives — never a classifier layer, never more few-shot examples.

Exam framing: "what should you check first" when Claude picks the wrong tool almost always wants: read/rewrite the tool descriptions.

Cert Schema anatomy: name, description (3–4 sentences — what, when, returns), input_schema. Claude reasons over the description text, not your implementation.

2. Errors are structured, not generic

Cert Tool errors returned to Claude should carry: isError + errorCategory (transient / validation / permission / business) + isRetryable + a human-readable description.

Never acceptable, each a distinct trap: a bare stack trace · total silence on failure · a uniform "Operation failed" regardless of cause (loses the retryable/non-retryable distinction Claude needs).

3. Tool sprawl degrades selection

Cert Loading 15+ tools onto a single agent measurably degrades selection accuracy. Fix: scope to 4–5 tools per role; add narrow cross-role tools only for genuinely high-frequency shared needs.

4. tool_choice — know the three values cold

  • auto — Claude decides whether to call a tool; plain text allowed.
  • any — Claude must call some tool, picks which; no text-only response.
  • {"type":"tool","name":"..."} — forces that specific tool. The mechanism for reliable structured-data extraction — read the payload from response.content[0].input.

Trade-off vs. pre-fill + stop-sequence: pre-fill is faster to set up, less reliable. Tool-forcing needs a real schema but wins whenever reliability matters more than simplicity.

5. MCP — architecture and the trap to avoid

Cert MCP is not an alternative to tool use — it's tool use with execution delegated to an external server. If an option frames MCP as competing with tool use, that's wrong by construction.

Three server primitives: Tools (actions, reactive — Claude decides to call) · Resources (data, proactive — pulled in without a tool call, direct or templated URIs) · Prompts (pre-built templates, slash-command style).

Trap: content that gets pulled in automatically when referenced is a Resource, not a Tool. Picking "add a tool that returns this" when the need is proactive/referenced access is a WRONG-PROBLEM miss.

Debugging: mcp dev [server_file.py] launches the MCP Inspector — browser UI to connect, browse tools/resources/prompts, manually invoke.

6. MCP configuration scope

  • Cert Team-shared → project .mcp.json, supports ${VAR} expansion, committed to source control.
  • Cert Personal/experimental → ~/.claude.json, not shared.

7. Built-in tools

ToolCustom code?Key facts
Text editorYes (execution only)Schema type string is version-pinned (3.5 vs 3.7 dates differ) — a real trap source.
Web searchNotype: web_search_20250305, max_uses caps searches, allowed_domains restricts scope.
Code executionNo (schema only)Docker container, no network access — Files API is the in/out channel.

Judgment layer — trap families this domain leans on

  • PROMPT-HOPE "add a note telling Claude which tool to prefer" instead of sharpening the description.
  • OVER-ENGINEERING a classifier layer to disambiguate tools instead of rewriting the two descriptions to be mutually exclusive.
  • NONEXISTENT FEATURE plausible-sounding but fake tool-config flags.
  • WRONG PROBLEM treating a resource-shaped need as tool-shaped; blaming "the tool" when the description was the defect.
Quick-reference / rapid recall
  • Tool selection failures → fix the description first, not a classifier.
  • Structured tool errors: isError + errorCategory + isRetryable + human-readable text. Never bare stack traces, never silence, never generic "failed."
  • 15+ tools degrades selection → scope to 4–5 per role.
  • tool_choice: auto (optional), any (forced, Claude picks), {"type":"tool","name":...} (forced, specific — reliable structured output).
  • MCP = tool use with execution delegated to a server, not a competing mechanism.
  • Resources = proactive/referenced data. Tools = reactive/invoked actions.
  • Config: .mcp.json (team) vs. ~/.claude.json (personal).
D3

Claude Code Configuration & Workflows

WEIGHT~20% · tied largest of the four
MOCK-6012 questions
DRAW-184 questions
BASISGap-filled from current docs
The domain your original course transcript covers least — genuinely Claude Code product mechanics, not generic API building. This is the fastest-moving domain in the exam's scope; verify anything version-specific.
Hardening note (post red-team): most of this file is grounded in official code.claude.com docs, but a few specifics came from dated third-party sources. If you have 10 minutes before the exam, verify: (1) the exact hooks event list and exit-code semantics in §2, (2) the precise CLAUDE.md precedence order when personal/project/managed rules genuinely conflict in §1, (3) whether allowed-tools frontmatter behaves identically in Claude Code CLI vs. the SDK in §3.

1. CLAUDE.md memory hierarchy

Cert Two complementary systems, both loaded at session start: CLAUDE.md files (instructions you write) and auto memory (notes Claude writes itself). Both are context, not enforced configuration — to guarantee an action regardless of what Claude decides, you need a hook (§2), not a memory file.

Locations, narrowest → broadest

  • CLAUDE.local.md — personal, project-specific, gitignored automatically.
  • Project ./CLAUDE.md — shared, committed, loaded for the whole team.
  • User ~/.claude/CLAUDE.md — personal preferences, applies across all projects.
  • Managed/enterprise policy CLAUDE.md — org-wide; cannot be excluded by any individual setting, always applies as a floor.

Likely Precedence: more specific overrides broader for content that actually conflicts — personal/local overrides shared project, project overrides user-global. Managed policy is a mandatory baseline that individual settings can't turn off. A user-level rule conflicting with a project-level rule in the same project → the project rule wins.

Likely Auto memory: stored at ~/.claude/projects/<project>/memory/, main file MEMORY.md — only the first ~200 lines load at session start, a hard budget. On by default; toggle via /memory or autoMemoryEnabled.

.claude/rules/*.md: every file loads automatically as project memory. A paths YAML frontmatter field (glob patterns) scopes a rule to matching files. Keep the main CLAUDE.md under ~200 lines; move detail into rules or skills.

2. Hooks — deterministic enforcement

Cert Hooks are user-defined event handlers that fire automatically at lifecycle points, regardless of what the model decides. This is the mechanism-level answer to "how do I guarantee X happens."

Key events to know
EventWhat it does
SessionStartFires at session start.
PreToolUseFires before a tool executes. Can allow/deny/ask/rewrite input. A deny is evaluated before any permission-mode check — blocks the tool even under bypass-permission modes.
PostToolUseFires after success; can inspect input/response; cannot undo the execution.
PreCompact / PostCompactBracket a context-compaction event; PostCompact receives the generated summary.
Stop / SubagentStopFire when the main agent / a subagent finishes responding.
UserPromptSubmitFires when the user submits a prompt.

Likely Exit-code protocol: exit code 2 from a PreToolUse hook stops the tool; exit code 2 from a Stop hook forces Claude to keep working.

Hooks vs. prompts: use hooks when compliance must be guaranteed — prompts have a non-zero failure rate, hooks are deterministic. "Must never happen" → hook-space. "Should usually happen" → prompt-space.

3. Agent Skills — SKILL.md

Cert A Skill needs at minimum a SKILL.md with required frontmatter name and description. Progressive disclosure: only name+description load at startup; full body loads only when relevant; bundled files load only if needed.

The description is the trigger, not documentation. Third person, lead with primary use case, real trigger phrases — same failure mode as D2's tool-description lesson, one layer up.

Notable frontmatter: allowed-tools, disable-model-invocation (explicit-invoke only — deploys, consequential actions), user-invocable: false (background knowledge), context: fork (isolated subagent context for verbose skill output).

Skills vs. CLAUDE.md vs. hooks

  • CLAUDE.md = always-in-effect context ("the constitution").
  • Skills = on-demand expertise, loaded when relevant ("the laws, invoked when applicable").
  • Hooks = deterministic enforcement, independent of the model's decision ("the police").

Judgment layer — traps specific to this domain

  • NONEXISTENT FEATURE — D3's signature trap. Fabricated CLI flags/config keys: --batch, CLAUDE_HEADLESS, inherit_context:true, parallel:true, context:compact, a commands array in config.json.
  • Edit-fallback trap — reaching for sed -i via Bash instead of Claude Code's documented Read+Edit/Write mechanism.
  • OVER-ENGINEERING — a custom hook-and-script pipeline for something a paths-scoped rule file already handles.
  • WRONG PROBLEM — blaming model reliability when the real issue is a CLAUDE.md context-budget problem.
Quick-reference / rapid recall
  • Memory hierarchy (narrow → broad, most-specific-wins): CLAUDE.local.md → project CLAUDE.md → user ~/.claude/CLAUDE.md → managed/enterprise policy (mandatory floor).
  • CLAUDE.md and auto memory are context, never enforcement — use hooks to guarantee behavior.
  • PreToolUse is the strongest hook — denies even under bypass-permission modes; exit code 2 stops the tool.
  • Hooks vs. prompts: guaranteed compliance → hook. Everything else → prompt/CLAUDE.md is fine.
  • SKILL.md requires only name + description; progressive disclosure loads the body on demand.
  • Personal vs. project scoping recurs identically across CLAUDE.md, skills, and MCP config — same pattern, three surfaces.
  • Signature traps: fabricated CLI/config flags, reaching for shell workarounds over native tools, blaming the model for a CLAUDE.md context-budget problem.

1. Core prompting techniques, ranked by typical impact

Exam framing: a corner case Claude keeps getting wrong despite a clear instruction almost always wants "add a one-shot example," not a more forceful rewrite or a bigger model.

2. Output control mechanics

  • Cert Pre-fill: seed the assistant message end (e.g. ```json); Claude continues from that exact point.
  • Cert Stop sequences: halt generation at a string; excluded from output.
  • Cert Tool-forced output (more reliable): tool_choice: {"type":"tool","name":"..."}, read from response.content[0].input. Pre-fill for quick/simple; tool-forcing when reliability > setup simplicity.

3. System prompts, temperature, role framing

Cert System prompts control how Claude responds, not what. Temperature 0 = deterministic (extraction, factual). Near 1 = creative (brainstorming, marketing).

4. Eval discipline

Six-step loop: draft → dataset → interpolate → run → grade → iterate.

  • Code graders — deterministic (JSON parses? AST parses? regex compiles?). Score 10 or 0. Needs known expected format in advance.
  • Model graders — a second Claude call scores the first. Ask for strengths/weaknesses/reasoning and score — never a bare score alone (regresses to middling).
  • Human graders — most flexible, least scalable.

5. Judgment layer — D4 is where PROMPT-HOPE lives

PROMPT-HOPE is the exam's most consistently recurring distractor, and it's fundamentally a D4 concept: a system-prompt line or few-shot example offered exactly where the stem signals the rule must always hold, needs guarantee/compliance, or has real financial/safety consequences. Cue words — "guarantee," "compliance," "never," "financial consequences" — mean the correct answer is a hook, gate, or schema, not anything living inside the prompt.

Two-question filter for any D4 scenario: (1) Is the failure "sometimes wrong" (prompt fix) or "must never be wrong" (not a D4 fix at all — D2/D3 territory)? (2) If it is a prompting fix, is the lever clarity, specificity, structure, or demonstration?

Secondary traps: OVER-ENGINEERING (fine-tuning/bigger model where a sharper prompt or one example would fix it — cue: "most effective first step"), DISPROPORTIONATE (rejecting an entire output class, or exhaustive constraint lists instead of a second targeted rewrite pass — the chaining-workflow lesson).

Quick-reference / rapid recall
  • Impact order: clear-and-direct → specificity (biggest lever) → XML structure → examples.
  • Type A guidelines (attributes) almost always; Type B (steps) for complex multi-perspective problems.
  • Pre-fill + stop sequence = fast structured output; tool_choice forcing = reliable structured output.
  • System prompt = how, not what. Temperature 0 = deterministic/extraction; near 1 = creative.
  • Eval loop: draft → dataset → run → grade → iterate. Code graders need known format; model graders need reasoning-plus-score.
  • The domain's core exam lesson: know when the fix stops being a prompting fix at all. "Must always / guarantee / compliance / financial consequences" → the answer lives outside the prompt.
  • Constraint-heavy prompts Claude keeps partially violating → a second targeted rewrite pass (chaining), not a longer single prompt.

Context Management & Reliability

WEIGHT~15% · smallest domain
MOCK-609 questions
DRAW-182 questions
BASISCourse material + gap-filled docs
Smallest domain by question count, but your second-weakest in the prior mock diagnostic — with the fewest questions, each miss costs proportionally more.
Hardening note (post red-team): the Batches API facts (§3) are docs-grounded and solid. The exact auto-compaction trigger threshold (§1) came from community reporting that conflicts across sources (85–95% depending on version/date) — don't memorize a specific percentage, lean on the mechanism instead. If a question forces a specific number, it's testing the mechanism, not asking for a percentage this file can verify with certainty.

1. Context compaction

Likely As a session grows, quality degrades before you hit a hard token ceiling ("context rot"). Compaction summarizes older content to free room while preserving what's needed.

  • Auto-compaction triggers automatically as context approaches the limit.
  • Manual /compact [instructions] — deliberate, optionally focused, can run proactively at a clean breakpoint.
  • PreCompact/PostCompact hooks bracket the event; PostCompact receives the generated summary.
  • Cannot be fully disabled — you steer what survives and when it fires, not whether it happens at all.
  • /clear wipes with no summarization — different from compaction, which preserves a lossy summary.
  • Session forking (--fork-session//branch) copies history into a new session, leaves the original intact.

Cert Server-side/API compaction is distinct: a beta strategy (context_management.edits) in the Messages API itself, triggered by an input-token threshold, wraps a summary in a <summary> block.

Reliability implication — the D5 judgment core: if Claude "forgets" an early instruction mid-session, it very likely only ever existed in conversation history and got summarized away at a compaction boundary. The fix is moving the constraint into a durable, always-reloaded surface (CLAUDE.md, a hook), not "reminding Claude more."

2. Prompt caching

  • Cert Max 1 hour. Fixed order: tools → system prompt → messages. Any change before a breakpoint invalidates the cache from that point forward.
  • Up to 4 breakpoints; layered caching allows partial hits.
  • Minimum 1024 tokens to be cache-eligible.
  • Longhand content-block form required — a plain string can't carry cache_control.
  • cache_creation_input_tokens (written) vs. cache_read_input_tokens (served from cache).

3. Message Batches API — the domain's hardest fact cluster

  • Cert Cap: 100,000 requests or 256 MB, whichever first.
  • Results within 24 hours, or the batch expires. Downloadable for 29 days.
  • 50% cost discount vs. synchronous, on input/output/cache tokens alike.
  • No minimum-latency SLA — anywhere up to the 24-hour outer bound.
  • Cannot be modified after submission; streaming not supported.
  • Tool use is supported inside a batch request — the real constraint is narrower: a batch cannot execute an iterative, multi-turn agentic tool loop. Each batch request produces exactly one response.
The trap: a scenario framing this as a speed problem is testing whether you fall for the more obvious-sounding but wrong explanation. It's architectural, not latency.

4. RAG — context management for external knowledge

Guess 7-step pipeline: chunk → embed → normalize → vector DB → embed query → similarity search → assemble prompt. Cosine similarity (closer to 1 = more similar) vs. cosine distance (closer to 0 = more similar) — inverses, classic mix-up trap.

Chunking: size-based (simple, needs overlap) · structure-based (best with reliable markdown/HTML structure) · semantic-based (most accurate, most complex). Hybrid search = vector + BM25, merged via Reciprocal Rank Fusion. Reranking = extra LLM pass after retrieval, worth it when retrieval nearly-but-not-quite captures intent. Contextual retrieval = prepend an LLM-generated situating blurb before embedding each chunk.

5. Reliability, more broadly

Cert Citations: citations: {enabled: true} + source title — verifiability, not blind trust. Extended thinking: use after prompt engineering has failed to hit target accuracy, confirmed via evals — not a first resort.

Judgment layer — traps specific to this domain

  • SILENT SUPPRESSION — D5's signature trap: empty-as-success, discarding a conflicting value, hiding a failure. Never correct in a reliability-framed scenario.
  • HEURISTIC GUESS — picking the most recent/prestigious value or averaging conflicting data. Correct move: ask for identifiers, or keep both annotated with source.
  • DISPROPORTIONATE — terminating a pipeline / reviewing 100% forever / rejecting a whole document class for a bounded problem.
  • WRONG PROBLEM — framing context-loss (compaction) as a model-reliability issue rather than a context-architecture one.
Quick-reference / rapid recall
  • Compaction preserves continuity under a shrinking budget; /clear wipes with no summary — pick based on continuity vs. clean slate.
  • Cannot fully disable compaction; steer what survives and when it fires.
  • Instructions living only in conversation history can be lost at a compaction boundary — durable rules belong in CLAUDE.md/hooks.
  • Prompt caching: 1hr max, tools→system→messages order, 4 breakpoints max, 1024-token minimum, longhand content blocks required.
  • Batches: 100k requests/256MB cap, 24hr window, 50% discount, cannot modify after submit, no streaming.
  • The Batches API's real limitation is architectural (no multi-turn tool loop), not merely latency — a known trap.
  • Cosine similarity (higher=closer) vs. cosine distance (lower=closer) are inverses.
  • Data conflicts → ask or annotate-and-keep-both. Never silently pick one, average, or suppress the discrepancy.
