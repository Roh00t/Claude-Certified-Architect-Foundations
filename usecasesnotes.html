UC1

Customer / Support Agent

ROLESingle agent, narrow cross-role tools
LEANS OND2 tool errors · D5 reliability
GROUNDINGYour own trainer's authored bank
Cert/Likely grounded in your own trainer's authored question bank — patterns recovered and paraphrased, not reproduced as A/B/C/D items.

An agent (often single-agent, sometimes with a narrow set of cross-role tools) handling customer-facing conversations — order lookups, refunds, disputes, complaints — where the stakes are real money, real customer trust, and a human escalation path that has to actually work when it's needed. This is where D2 (tool errors) and D5 (reliability/context) show up most concretely.

D1 — Orchestration

  • Multi-issue messages (damaged item + duplicate charge + wrong address, one message) should be decomposed into distinct items, investigated with shared context, and synthesized into one unified resolution. Traps: answering only the first issue and deferring the rest (BURDEN-SHIFT), escalating just because the message has multiple parts (DISPROPORTIONATE), handling everything in one undifferentiated pass (risks quietly dropping a sub-issue).
  • Escalation calibration: an agent that escalates straightforward cases while attempting complex policy-exceptions autonomously has an unclear-decision-boundary problem. Fix: explicit escalation criteria plus worked examples — not a self-reported confidence score (circular — an already-miscalibrated agent miscalibrates its own confidence too), not a separately trained classifier (over-engineered).
  • Human handoff with no transcript access needs a structured summary — customer ID, root-cause analysis, disputed/refund amount, recommended action. Not the raw reasoning chain (unreadable), not a vague "too complex for AI" note (forces the human to start from zero).

D2 — Tool design

An agent calling get_customer when the user really wants lookup_order is a description problem, not a data problem — fix by enriching both descriptions with input formats, example queries, and explicit boundaries. Not a routing/keyword layer, not a bigger few-shot block.

Structured tool errors matter most here: an agent getting "Operation failed" for everything will retry a policy-violation error pointlessly and give up on a transient timeout it should have retried. This is where the abstract D2 rule has the most obviously bad real-world consequence if skipped.

D3 — Claude Code / configuration

Less central here than in Developer Productivity or CI/CD, but standing policy that must always apply (refund caps, required identity verification) belongs in a hook, not a system prompt — a support agent operates on real financial actions where occasional probabilistic failure is unacceptable.

D4 — Prompting

The escalation-criteria fix above is a direct D4 technique (specificity + examples) applied to a D1-shaped problem — illustrates why these use-case questions need cross-domain thinking. Watch for PROMPT-HOPE bait: "add a stronger system-prompt line telling the agent never to approve refunds over $500" when the stem's stakes are exactly the cue the real answer is a hook.

D5 — Context and reliability

The signature D5 pattern here: long multi-issue sessions get progressively summarized, and exact amounts/dates/order numbers erode into vague language ("a recent order, roughly $200") — producing wrong refund figures. Fix: a persistent case-facts block (amounts, dates, order numbers, statuses) that sits outside the summarized history and is included verbatim every prompt. Wrong answers: never summarizing at all (exhausts context), summarizing more aggressively (makes drift worse), repeatedly asking the customer to restate numbers (erodes trust, gets summarized away again anyway).

Signature traps for this use case

  • BURDEN-SHIFT "ask the customer to resend issues one at a time," "ask the customer to confirm the AI's own uncertain output."
  • DISPROPORTIONATE escalate every multi-part message; terminate the session on any ambiguity.
  • SILENT SUPPRESSION quietly dropping one issue from a multi-issue message; letting summarization erode a dollar figure without flagging it.
  • PROMPT-HOPE financial/compliance stakes answered with a system-prompt instruction instead of a hook.
Quick-reference
  • Multi-issue input → decompose, shared context, unified synthesis.
  • Escalation drift → explicit criteria + examples, not self-reported confidence or a new classifier.
  • Handoff to a human with no transcript → structured summary (ID, root cause, amount, recommendation).
  • Generic "Operation failed" → structured error shape (category/retryable/human-readable).
  • Numbers eroding over a long session → persistent case-facts block outside the summarized history.
  • Financial/compliance "must never" language → hook, not a prompt line.
UC2

Multi-Agent Research

ROLECoordinator + specialized subagents
LEANS OND1 orchestration · D2 scoping · D5 aggregation
GROUNDINGYour own trainer's authored bank
Cert/Likely grounded in your own trainer's authored question bank — patterns recovered and paraphrased, not reproduced as A/B/C/D items.

A coordinator agent dispatching specialized subagents (web-search, analysis, synthesis) to investigate a topic and produce a combined report. D1's home turf almost by definition — coordinator/subagent architecture, parallelism, isolation — but pulls D2 and D5 in hard too.

D1 — Orchestration (the core of this use case)

  • Error propagation from a failing subagent: when a web-search subagent times out, the coordinator needs structured error context — failure type, attempted query, partial results, potential alternatives — so it can retry modified, route around, or proceed with partial results. Traps: retrying silently and returning generic "search unavailable" (hides context needed to decide), catching the timeout and returning an empty result marked successful (SILENT SUPPRESSION), propagating to a handler that terminates the entire workflow (DISPROPORTIONATE).
  • Subagent isolation is load-bearing: each subagent gets a fresh context window, returns only its final message. A synthesis agent doesn't automatically "know" what a search subagent found unless explicitly passed forward.
  • Parallel dispatch: independent research subtasks should be spawned as multiple calls in a single coordinator turn, not chained sequentially.

D2 — Tool design in a multi-agent context

Cross-role tool scoping: when 85% of a synthesis agent's verifications are simple fact-checks and 15% need deep investigation, routing everything back through the coordinator adds unnecessary round trips. Right fix: a scoped verification tool given directly to the synthesis agent for the simple case, complex verifications still go through the coordinator — least-privilege scoping. Traps: full web search access to the synthesis agent (over-provisions), batching all verifications to the end of a pass (blocking dependencies), speculative caching around every source (can't predict needs).

Description-driven misrouting: two similarly-named analysis tools with near-identical descriptions → rename and differentiate, not a system-prompt keyword rule (brittle) and not lowering temperature (doesn't resolve genuine ambiguity).

D3 — Claude Code / configuration

Subagent definitions (.claude/agents/*.md or the agents SDK parameter) are the concrete D3 mechanic underlying this use case's architecture. SubagentStop hooks are the natural fit for gating a subagent's result before the coordinator folds it in.

D4 — Prompting

The prompt written for each subagent matters more here than almost anywhere else — it's the only information channel (D1's isolation rule again). A vague dispatch prompt is functionally the same failure as a vague tool description in D2.

D5 — Context and reliability

Lost-in-the-middle on aggregated findings is this use case's signature D5 pattern: findings from six subagents concatenated into one long synthesis input → content from the middle is disproportionately likely to be dropped. Fix: a key-findings summary at the beginning + explicit section headers — structure fights positional bias directly.

Signature traps for this use case

  • SILENT SUPPRESSION a failed subagent search returning an empty result marked as success.
  • DISPROPORTIONATE terminating the whole multi-agent workflow over one subagent's recoverable failure.
  • OVER-ENGINEERING granting full tool access instead of one scoped tool for the high-frequency simple case.
  • WRONG PROBLEM blaming "the subagent" or "the model" when the defect is the coordinator's dispatch prompt or aggregation structure.
Quick-reference
  • Subagent failure → structured error context to the coordinator — never silent-empty-success, never a full workflow kill.
  • Subagents inherit nothing automatically — the dispatch prompt is the only channel; write it like a tool description.
  • High-frequency simple sub-need → a scoped cross-role tool, not a blanket capability grant.
  • Findings from the middle of a long aggregated input vanish → summary-first + explicit section headers.
  • Parallel independent subtasks → multiple spawn calls in one coordinator turn.

Claude generating, editing, or reviewing code — either via the raw API (structured code as output) or via Claude Code / the Agent SDK (an agent with file and shell access actually modifying a codebase). Likely tests both: the right prompt/schema for code output (D4) and the right tool/workflow discipline for an agent editing real files (D3/D1).

D1 — Orchestration

  • Workflow vs. agent is a live decision, not academic: a well-specified change (add a field, rename a function, fix a known bug) is a workflow. An open-ended "improve test coverage" task is agent-shaped. A scenario proposing a full autonomous agent for a well-specified task is testing whether you'll over-reach for flexibility you don't need.
  • The three-step method (identify files → plan, no code yet → implement the approved plan) is a chaining pattern; test-driven development (context → propose tests → select → write code until tests pass) is an evaluator-optimizer pattern where the tests are the evaluator.
  • Environment inspection is non-negotiable: read a file before modifying it, verify after (run the test, check the diff) rather than assuming the edit landed as intended.

D2 — Tool design

The Edit-fallback trap belongs here as much as in D3: reaching for sed -i via Bash instead of the platform's Read+Edit/Write mechanism is a tool-selection failure specific to coding agents. Structured tool errors matter for edit tools specifically — a failed edit needs to say why (pattern not found vs. file changed since last read), or the agent will blindly retry or guess at the wrong file.

D3 — Claude Code configuration

PostToolUse hooks are the mechanism for “always run the formatter/linter after every write” — a code-generation-flavored instance of “hooks guarantee, prompts merely request.” Project CLAUDE.md is where build/test commands and conventions belong — verbatim exact strings, since the model uses them literally.

D4 — Prompting and structured output

For raw-API code generation: pre-fill ```python + stop sequence ``` is the fast path to clean output; tool_choice-forced extraction is the reliable path for an automated pipeline. Code-based grading is the natural evaluator: validate_python() (AST-parses → 10, else → 0) is cheap and deterministic — evaluating generated code quality at scale wants this before a model grader.

D5 — Context and reliability

Long coding sessions are where compaction bites hardest: an early architectural decision ("we use the repository pattern," "never touch legacy/") made early can be summarized away later. Durable decisions belong in CLAUDE.md, not just conversation history. For large codebases, targeted grep/glob reading is the coding-agent equivalent of RAG's "retrieve only the relevant chunk" principle.

Signature traps for this use case

  • NONEXISTENT FEATURE a plausible-sounding but fake Claude Code flag offered as the fix.
  • OVER-ENGINEERING a full autonomous agent for a well-specified task a three-step workflow would complete more reliably.
  • WRONG PROBLEM blaming "the model can't code well" when the real gap is a missing TDD loop or an unfocused CLAUDE.md.
  • PROMPT-HOPE "tell it in the system prompt to always run the formatter" instead of a PostToolUse hook.
Quick-reference
  • Well-specified code task → workflow (three-step or TDD). Open-ended improvement task → agent, only if genuinely unpredictable.
  • Formatting/linting that must always happen → PostToolUse hook, never a prompt reminder.
  • Edit a file the agent has access to → native Read+Edit/Write, not a shell workaround.
  • Clean code output fast → pre-fill + stop sequence. Reliable code output for a pipeline → tool-forced extraction.
  • Evaluating generated code at scale → code grader (AST/syntax validity) before model grader.
  • Architectural decisions that must survive a long session → CLAUDE.md, not just conversation turns.

Claude Code (or the Agent SDK) as a developer's day-to-day tool — memory, skills, parallel work via worktrees, automated maintenance tasks. Where Code Generation is about a single task's output quality, this use case is about the system around the developer's workflow. Most D3-heavy of the six use cases, with real D1 content around parallelization.

D3 — Claude Code configuration (the core of this use case)

  • The full memory hierarchy is fair game here: which file a piece of context belongs in (personal preference vs. team convention vs. org-wide policy) is exactly what this use case tests. A rule for one developer only, one project's team, or an entire org → CLAUDE.local.md / project CLAUDE.md / managed policy respectively.
  • Skills vs. CLAUDE.md vs. hooks: "a developer keeps re-explaining how to run our deploy script" → wrap it as a skill (on-demand) rather than bloating always-loaded CLAUDE.md.
  • Auto memory's 200-line load budget: stuffing routing rules/boilerplate into auto memory instead of CLAUDE.md burns a meaningful fraction of a hard, capped budget.

D1 — Orchestration (parallelization specifically)

  • Git worktrees run multiple Claude Code instances on the same repo without conflicts — each worktree a full isolated copy on its own branch, merges back after. This use case's version of D1's subagent-isolation principle, applied at the session level.
  • Custom commands (.claude/commands/*.md with $ARGUMENTS) automate the worktree create/assign/merge/cleanup cycle — the gain is "a virtual team," bounded by the developer's management capacity, not the tooling.
  • The automated production debugging pattern (scheduled GitHub Action → pull logs → dedupe/analyze → generate fixes → open a PR) is a workflow, not an agent — fully predetermined, which is exactly why it's reliable enough to run unattended.

D2 — Tool design

Developer-productivity tooling tends to reach for broad, general-purpose tools (bash, file read/write, web fetch) rather than narrow single-function ones — D1's abstraction principle showing up as a D2 tool-inventory decision.

D4 — Prompting

Detailed, specific instructions to a coding-productivity agent produce meaningfully better results than vague ones — the course's explicit "effort multiplier" framing, the same specificity lesson from D4's core content viewed as a developer-experience principle.

D5 — Context and reliability

Compaction control is a genuine productivity lever, not just a safeguard: proactively running /compact at a clean breakpoint (rather than letting auto-compact fire mid-task) is a deliberate developer habit. "Session getting sluggish / forgetting earlier decisions" over a multi-hour session tests this same D5 mechanism through a productivity lens. Session forking is the productivity-flavored version of protecting durable state before it can be lost.

Signature traps for this use case

  • NONEXISTENT FEATURE fabricated CLI flags/config keys — especially tempting here since this use case is about configuration.
  • OVER-ENGINEERING building custom external tooling to solve something git worktrees, a skill, or a rules file already solves natively.
  • WRONG PROBLEM treating "Claude Code ignored my instruction" as an inherent limitation when the real cause is CLAUDE.md length/scope.
  • BURDEN-SHIFT "have the developer manually re-explain project context every session" instead of using CLAUDE.md/auto memory.
Quick-reference
  • Scope of a rule (personal / team / org) determines which memory file it belongs in — a recurring, direct exam pattern.
  • Occasionally-needed procedure → skill. Always-needed context → CLAUDE.md. Must-always-happen rule → hook.
  • Parallel Claude Code instances on one repo → git worktrees, not manual coordination.
  • A fully predetermined, schedulable maintenance task → workflow, not an agent — needs to run reliably unattended.
  • Session getting sluggish/forgetful over hours → proactive /compact or session forking at a clean breakpoint.

CI/CD

ROLEUnattended pipeline automation
LEANS OND1 workflow default · D3 hooks · D5 Batches
GROUNDINGSynthesized — verify
Likely grounded in course material / official docs for mechanics. Guess synthesized for this use case specifically.
No prior grounding: no verified prior trainer questions of yours to ground this one. The highest-risk claim in this file is the Batches-API-in-CI/CD framing — cross-check it against D5's Batches section (docs-grounded) rather than treating this file's application of it as independently verified.

Claude integrated into an automated pipeline — running unattended, triggered by git events or a schedule, with no human in the loop to catch a mistake in real time. The use case where the exam's “must always / guaranteed” language is most literally true rather than just scenario flourish.

D1 — Orchestration

  • "Workflow, not agent" is almost always right here, more than in any other use case — CI/CD by definition means the steps are known in advance (lint → test → build → deploy). A dynamic-planning agent for a well-understood pipeline is very likely OVER-ENGINEERING dressed as flexibility.
  • The automated debugging pattern (scheduled trigger → pull logs → analyze/dedupe → generate fix → open PR, never auto-merge) is this domain's canonical example — predetermined, unattended-safe, and stops at a PR, not a merge. Direct merging/deploying without a human or a deterministic gate is a red flag in most framings.

D2 — Tool design

Tool permission scoping is sharper-edged here than anywhere else: unattended pipeline access (full filesystem, unrestricted bash, production credentials) is a materially different risk than the same tools in an interactive session where a human approves each action. Structured retryable-vs-not error signaling matters even more, because a pipeline has to decide automatically whether to retry, fail, or continue — no human makes that call live.

D3 — Claude Code configuration

PreToolUse hooks are the actual enforcement mechanism for CI/CD guardrails — a hook denying a dangerous command fires before the tool executes and evaluates before any permission-mode check, meaning it can't be bypassed even in a fully automated pipeline context. The single highest-yield D3 fact for this use case. Managed/enterprise-policy CLAUDE.md is relevant specifically because it cannot be excluded by a pipeline's own project-level configuration.

D4 — Prompting

Structured, machine-parseable output is close to mandatory since the next pipeline step is code, not a human reading prose — tool_choice-forced output is generally the more defensible choice, since "reliability > setup simplicity" is close to always true for an unattended step another script will parse.

D5 — Context and reliability

The Message Batches API's real constraint is a genuine CI/CD design question: bulk latency-tolerant operations (nightly evals, bulk classification of a backlog) are a legitimate Batches use case at 50% cost — but anything needing Claude to call a tool, see the result, and decide the next step cannot go through Batches, since a batch request is single-turn only. Prompt caching is a natural fit here too — pipeline runs frequently repeat identical system prompts and tool schemas across builds.

Signature traps for this use case

  • PROMPT-HOPE at its most literal — no human in the loop to catch a failure is genuinely true here, not just scenario flavor.
  • OVER-ENGINEERING a dynamic-planning agent for a pipeline whose steps are actually fully known in advance.
  • DISPROPORTIONATE failing the entire build/pipeline run on an error category that should have been a scoped retry.
  • WRONG PROBLEM framing a Batches-API latency complaint as "make the batch bigger" when the actual issue is a needed iterative tool loop Batches can't provide.
Quick-reference
  • CI/CD steps are almost always known in advance → workflow is the default, not an agent.
  • Automated fix pattern stops at a PR — not an auto-merge — unless a deterministic gate explicitly replaces human review.
  • Guardrails that must hold with zero human oversight → PreToolUse hooks specifically, never a prompt instruction.
  • Org-wide rules that must apply even to pipelines teams configure themselves → managed/enterprise CLAUDE.md.
  • Next-step-is-code output → tool-forced structured output over pre-fill/stop-sequence.
  • Bulk, latency-tolerant, single-turn-per-item work → Batches API. Anything needing mid-task tool-informed continuation → not Batches.

Data Extraction

GROUNDINGSynthesized — verify

No prior grounding: no verified prior trainer questions of yours to ground this one. Run a few AI-mode questions tagged toward D4/D5 and check whether real questions lean more tool-forcing-vs-prefill (this file's emphasis) or more RAG/chunking (treated as secondary here) — that balance is inference, not a verified pattern.

Pulling structured data out of unstructured or semi-structured sources — documents, PDFs, images, scraped text — at scale, usually feeding a downstream system that expects clean, parseable output. D4's structured-output content and D5's reliability content applied together, plus D2's tool layer when the source material itself needs processing first.

D4 — Structured output (the core of this use case)

The pre-fill/stop-sequence vs. tool-forced-extraction decision is the central D4 question here, and this use case tips hardest toward tool-forcing: an extraction pipeline almost always feeds something downstream that breaks on malformed JSON, so tool_choice against a real schema is generally the more defensible default — pre-fill is better reserved for quick/one-off extractions.

Code-based grading is the natural evaluator: validate_json() (parses → 10, else → 0) is a cheap, deterministic, directly-relevant check — quality starts with "is this even valid JSON" before semantic correctness.

D5 — Reliability (the domain's other core)

HEURISTIC GUESS is this use case's signature trap. When extracted data conflicts across sources, the correct move is to ask for clarification/identifiers, or keep both values explicitly annotated with their source — never silently pick the most recent one, the "more prestigious" source, or an average.

Citations exist specifically for this use case's verifiability problem — letting a downstream consumer check where an extracted value came from rather than trusting the extraction blind. Cosine similarity vs. distance matters concretely if extraction involves retrieving the right source chunk first. Large documents needing field-level extraction are a direct RAG use case: chunk, retrieve the relevant section, extract from that section specifically.

D2 — Tool design

Files API + code execution is the mechanism when source material needs processing before extraction is possible — a scanned PDF, a spreadsheet needing parsing first. Structured tool errors matter for partial extraction failures: a batch pipeline needs to know which specific document failed and why, not a generic failure signal that forces reprocessing the entire batch.

D1 — Orchestration

Bulk extraction across many independent documents is a parallelization workflow almost by definition — each document's extraction is independent, exactly the shape that benefits from parallel dispatch rather than sequential one-at-a-time processing.

D3 — Claude Code configuration

Least central of the five here, but a skill packaging a specific document format's extraction conventions is a legitimate on-demand home for that domain knowledge — relevant if Claude Code is processing a batch of files from disk rather than the raw API.

Signature traps for this use case

  • HEURISTIC GUESS picking the most recent/prestigious source, or averaging conflicting values, instead of asking or annotating both.
  • SILENT SUPPRESSION dropping a field that failed to extract instead of surfacing it as missing/uncertain; a batch job reporting success while silently skipping malformed records.
  • OVER-ENGINEERING building a custom classifier to route documents by type when a sharper extraction-tool schema would already disambiguate them.
  • DISPROPORTIONATE failing an entire batch extraction job because one document in a thousand was malformed.
Quick-reference
  • Production extraction pipeline → tool-forced structured output over pre-fill/stop-sequence, most of the time.
  • Validity check for extracted output → code grader (JSON/schema validation) before a model grader.
  • Conflicting extracted values → ask for identifiers, or keep both annotated with source. Never guess, average, or silently pick one.
  • Need to verify where an extracted value came from → citations, not blind trust in the synthesis.
  • Large source document → chunk and retrieve the relevant section before extracting.
  • Many independent documents → parallelize; one bad document → flag and continue, don't fail the whole batch.
